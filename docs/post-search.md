# 커뮤니티 글 검색 · 키워드 + 임베딩 하이브리드

`GET /posts?q=달걀&board=recipe&limit=20`으로 로그인 후 검색한다. 구현은 `app/services/post_search.py`의 `find_posts()` 한 곳이고, 라우터와 앱은 같은 API(`{posts, next_before_id}`)를 그대로 쓴다.

## 동작

- **검색어(`q`)가 없거나 공백이면** 예전과 같은 최신순 목록이다. 이때 `before_id`는 "이 글 번호보다 오래된 글부터"다.
- **검색어가 있으면(최대 100자)** 관련도순이다. 글마다 `점수 = 키워드 점수 × 0.6 + 의미 점수 × 0.4`를 매기고, 점수가 0인 글은 결과에서 빠진다. 점수가 같으면 최신 글이 먼저다.
  - **키워드 점수**(0~1): 검색어 전체가 제목에 있으면 1, 본문에 있으면 0.85. 아니면 검색어를 단어로 나눠(최대 8개) 제목에 있으면 1, 본문에만 있으면 0.7로 세어 맞은 비율 × 0.9. 그래서 `달걀 후기`처럼 단어가 떨어져 있어도 찾고, 단어가 더 많이 맞는 글이 앞에 온다. 영문 대소문자는 구분하지 않고 `%`, `_` 같은 문자는 그냥 글자로 취급한다.
  - **의미 점수**(0~1): 글(제목 2번 + 본문 앞 300자)과 검색어를 벡터(임베딩)로 바꿔 코사인 유사도를 구한다. 유사도 0.2 미만은 "관련 없음"(0점), 그 위로는 1에 가까워질수록 높다.
  - **식재료 별칭**: 글과 검색어를 비교하기 전에 `계란→달걀`, `쇠고기→소고기`, `야채→채소`로 맞춘다(`app/services/embeddings.py`의 `FOOD_ALIASES`). 그래서 `계란말이`로 `달걀말이` 글이 나온다.
- **다음 쪽**: 응답의 `next_before_id`를 그대로 `before_id`로 보낸다(앱은 이미 그렇게 한다). 검색 중에는 관련도순이라 글 번호로 이어 붙일 수 없어서 `next_before_id`가 "이미 받은 결과 수"다. 쪽을 넘기는 사이에 글이 새로 생기거나 고쳐지면 순위가 달라져 한두 개가 겹치거나 빠질 수 있다.
- 삭제된 글 제외, 게시판(`board`) 필터, 로그인 보호는 두 경우 모두 같다. 일반 글과 자동 등록된 레시피 후기 모두 검색된다.

## 임베딩

- 제공자는 `local` 하나다(`EMBEDDING_PROVIDER`, 기본값). 외부 서비스·키·모델 파일 없이 서버 안에서 계산한다. 글을 단어로 나누고 단어와 그 안의 글자 2~3개 묶음을 512칸 벡터에 해시로 섞어 길이를 1로 맞춘 것이다.
- **잘하는 것**: 조사·어미가 다른 말(`달걀을` → `달걀말이`), 일부만 맞는 단어, 흔한 오타. 짧은 글(제목)에서 특히 잘 맞는다.
- **못하는 것**: 글자가 전혀 다른 동의어와 문장의 뜻(별칭표에 넣은 몇 개만 예외). 긴 글에서는 글자 조합이 희석되어 의미 점수가 낮아지고, 그런 글은 주로 키워드 점수로 찾힌다. 실제 의미 검색이 필요하면 아래 "신경망 임베딩으로 바꾸려면"을 본다.
- **저장**: `post_embeddings` 표(마이그레이션 `0013`). 글을 쓰고 고치고 지우는 코드는 이 표를 모른다. **검색할 때** 벡터가 없거나 낡은 글(내용 해시나 `model` 이름이 다름)만 새로 만들어 저장한다. 한 번의 검색에서 최대 500개이므로, 기존 글이 많으면 배포 직후 몇 번의 검색에 걸쳐 채워지고 그동안 아직 벡터가 없는 글은 키워드 점수로만 순위가 정해진다.
- **다시 만들기**: 글이 바뀌면 자동이다. 알고리즘·차원·별칭표를 바꾸면 `LocalNgramEmbedder.name`이 달라져야 저장된 벡터가 새 방식으로 다시 만들어진다(별칭표는 이름에 자동 반영, 알고리즘을 바꿀 때는 이름의 `v1`을 올린다. `tests/test_post_search.py`의 고정값 검사가 알려 준다).
- **범위와 속도**: 한 번의 검색에서 최신 2000개 글(`POOL_SIZE`)의 점수를 계산하고, 그보다 오래된 글은 검색어 전체가 글자 그대로 들어 있는 것만 더한다. 글 2000개일 때 검색 한 번이 개발 컨테이너의 PostgreSQL 16에서 약 0.16~0.23초였다. 글이 수천 개를 넘으면 DB에서 벡터를 찾는 방식(pgvector 등)이나 검색 엔진으로 옮긴다.
- **끄기**: `EMBEDDING_PROVIDER=none`으로 다시 시작하면 키워드 점수만 쓴다. 저장된 벡터는 지우지 않고 쓰지도 않는다.
- **장애**: 벡터를 만들지 못하면 오류 대신 키워드 점수만으로 정상 응답한다. 벡터 저장이 실패해도(동시에 같은 글을 저장하는 등) 이번 검색은 정상이고 다음 검색이 다시 시도한다.

## 배포 순서와 되돌리기

`alembic upgrade head`로 `0013`을 먼저 적용한 뒤 서버를 올린다(표가 없으면 검색어가 있는 요청이 실패한다. 검색어가 없는 목록은 새 표를 쓰지 않는다). 앱은 바꿀 것이 없다. 이전 서버로 되돌려도 새 표는 쓰이지 않을 뿐 해롭지 않고, `alembic downgrade 0012`로 표를 지울 수 있다.

## 신경망 임베딩으로 바꾸려면

`app/services/embeddings.py`의 `Embedder` 모양(`name`, `min_similarity`, `embed_documents()`, `embed_query()`)을 구현한 제공자를 만들고 `get_embedder()`와 `Settings.embedding_provider`에 연결한다. 저장·점수 합산·정렬·쪽 넘기기는 그대로 쓴다. 모델마다 코사인 유사도의 분포가 달라 `min_similarity`는 실제 글로 맞춰야 한다. 외부 API를 쓰면 글 내용이 그 서비스로 전송되고 키와 호출 비용이 생긴다. 호출이 실패하면 `EmbeddingError`를 던지면 검색은 키워드 점수로 대체된다.

## 앱 연결과 검증

앱은 `src/features/service/community-model.ts`의 `postsPath()`와 `community.tsx`의 검색 입력·적용 검색어 상태로 같은 API를 부른다(검색 방식이 바뀌어도 고칠 것이 없다). 검증: `tests/test_post_search.py`, `tests/test_community.py`, `tests/test_recipe_reviews.py`, `tests/test_migration_0013.py`, 앱의 `tests/community-boards.test.mjs`.
