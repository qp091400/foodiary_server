# 식재료 기반 레시피 추천

## 여러 출처 통합 (2026-10-29)

기존 COOKRCP01 전체 자료, 농식품 포털의 기본정보/재료정보/과정정보,
사용자가 KADX에서 내려받은 만개의레시피 CSV를 통합한다.
농식품 포털에서 세 API를 신청하고 호출 PC의 공인 IP를 등록한 뒤
`.env`의 `MAFRA_API_KEY`를 설정한다. 키는 앱이나 Git에 넣지 않는다.

```sh
python3 -m scripts.prepare_recipes
docker compose up --build -d
docker compose run --rm --no-deps --volume /absolute/path/to/csvs:/imports:ro api python -m scripts.import_recipe_sources --mafra --csv /imports/TB_RECIPE_SEARCH-220701.csv /imports/TB_RECIPE_SEARCH-231130.csv /imports/TB_RECIPE_SEARCH_241226.csv /imports/TB_RECIPE_SEARCH_251231.csv
```

첫 수집 전 기존 `scripts.import_recipes`로 식약처 전체 자료를 준비한다.
CSV는 CP949/UTF-8을 판별하고 재료 안의 구분 문자와 분량을 정리한다.
같은 출처의 레시피 번호는 최신 파일을 우선하며 다른 출처의 번호는
`mafra:` / `10000recipe:` 접두어로 충돌을 방지한다. 기존 식약처 ID는 호환을 위해 유지한다.
같은 이름의 다른 조리법은 별개 레시피로 보존한다. 따라서 통합 건수는
고유한 요리 이름의 수가 아니라 출처별 고유 레시피의 수다.

재료가 없는 레코드나 이름/재료에 깨진 문자가 있는 레코드는 추천 색인에서 제외한다.
만개의레시피 CSV에는 조리 순서와 사진이 없으므로 단계는 빈 배열로 보존한다.
소개글을 단계로 바꾸거나 사이트를 추가 수집하지 않는다. 상세에서 원문 링크를 제공한다.
CSV 이용조건은 다운로드 상품의 조건을 따른다. 원문 링크가 삭제되었거나 제공자의 접근 정책이
변경된 경우 원문에서 조리법을 확인하지 못할 수 있다. Git 저장소 공개가 데이터 재배포 허가를 뜻하지 않는다.

결과는 `RECIPE_DATA_DIR/recipes.sqlite3`에 저장한다. 재료별 색인을 통해 선택한 모든
재료의 교집합을 찾고 부족 재료 개수순, 동순위 무작위로 30개를 고른다.
공식 자료의 조리 순서와 CSV의 원문 안내를 하나의 기존 응답 형식으로 전달하며
조리시간·난이도·인분 정보를 선택적으로 추가한다. 요청 중 외부 API를 호출하지 않는다.
추천 응답의 `display_name`은 카드용 음식 이름이다. CSV의 별도 요리명(CKG_NM)을 우선하며
없는 자료는 제목에서 명확한 작성자 표기/수식어/레시피 안내 문구만 정리한다.
`name`에는 원래 제목을 그대로 보존하고 상세 화면에서 줄 수 제한 없이 표시한다.
표시 이름은 요청 시 계산하므로 기존 데이터 파일을 다시 가져올 필요가 없다.

수집 성공 후에만 SQLite 파일을 원자적으로 교체한다. 농식품 원본은
`mafra-source.json`, 수집 파일의 해시/출처별 건수는 SQLite 메타데이터에 보관한다.
원본·색인은 기존 `recipe_data` 영속 볼륨에 있으며 Git에서 제외된다.
개발 이미지에는 아래 데이터 준비 절차로 검증한 레시피 DB만 포함한다.
팀원이 별도 서버를 실행하거나 배포할 때는 이용조건에 맞게 이 볼륨의 데이터 파일을
비공개 저장소로 전달/복원하거나 같은 수집 명령을 실행해야 한다. 코드만 pull해도
레시피 데이터가 자동 전달되는 것은 아니다. 운영에서는 이 파일들을 비공개 객체 저장소에서
복원해 영속 마운트에 배치한다. 자동 클라우드 업로드 기능은 포함하지 않는다.

식약처만 다시 수집한 경우 통합 명령도 다시 실행해야 색인에 반영된다.
`--mafra` 없이 실행하면 저장된 농식품 원본을 재사용한다. CSV는 재구축할 때 전체 파일 목록을 전달한다.
검사: `pytest -q tests/test_recipes.py tests/test_recipe_sources.py`.

### 추천 자료 선별

원본 레시피는 보존하면서 추천 대상만 선별한다. 품질 규칙 v4는 분류에 관계없이
전체 자료의 제목·요리명·재료·음식 분류를 검사한다. 까기/깎기/자르기/썰기/다지기/세척/
손질/해감/해동/보관/소분/장식 등 준비 작업 중심의 글은 제외한다. 요리명이 제목에
실제로 등장하는 완성 요리와 함께 안내된 팁은 보존하지만, '김밥 재료 손질법'이나
'장조림용 메추리알 까는법'처럼 음식 이름만 빌린 안내는 제외한다.
무·대파·밀가루 같은 부재료가 들어가도 '문어 삶는 법', '문어숙회 삶기', '굽는 방법',
'찌는 법'처럼 단순 조리 안내인 자료는 제외한다. '문어초회 만들기와 문어 삶는 방법'처럼
완성 조합 요리명이 제목에 명시된 자료는 보존한다.
또한 숙회/구이 이름으로 등록돼 있어도 해당 식재료에 무·대파·밀가루 같은 손질/삶기
보조재료만 추가된 자료는 제외한다. 냄비/프라이팬/호일의 설명형 표기와 기름장/청주 같은
보조 항목도 조합 식재료 수를 늘리는 근거로 사용하지 않는다.
반려동물용 음식, 비누/세제/냅킨 등 생활정보, 모음/주간 식단, 주재료 확인 불가,
요리명과 완성 요리의 근거가 부족한 자료도 추천에서 보류한다.
조합 추천을 위해 서로 다른 식재료가 최소 2종 있어야 한다. 물·기본 양념(STAPLES)·도구는
식재료 종류 수에 포함하지 않는다. 얼음·찬물·뜨거운 물·'물 넉넉히/잠길 정도' 등의 표현,
당류/조리유/베이킹소다 같은 보조재료도 독립적인 조합 재료로 세지 않는다.
달걀/계란 등 정규화한 같은 재료의 반복 표기도 1종이다.
베이컨 단독, 베이컨+물/소금/후추/기름, 삶은 달걀, 군고구마 같은 단독 레시피는 제외한다.
이 조건은 수동 include로도 해제되지 않으며 수집 색인과 요청 시 추천 양쪽에서 검사한다.
선택 재료가 1종이라는 이유로 조합 레시피를 막지는 않는다. 베이컨을 선택하면
베이컨+달걀 등 2종 이상을 사용하는 요리는 부족 재료를 표시해 추천할 수 있다.
자동 판단은 원문 조리과정의 전수 검증을 의미하지 않으며, 애매한 자료는 보류 후 개별 복원할 수 있다.
선별 이유는 SQLite의 `exclusion_reason`에 기록하며, 기존 레시피 ID로 상세 조회는 계속 가능하다.

동일한 요리명(CSV의 CKG_NM 우선), 전체 재료명 조합, 조리방법을 가진 자료는 묶어서
대표 하나만 추천한다. 계란/달걀 등 일부 표기 차이를 통일하고 분량 차이는 같은 묶음으로
취급한다. 조리 순서가 있는 자료를 먼저 대표로 고르며 서로 다른 재료 조합은 별개로 둔다.
이는 보수적인 중복 억제이며 의미가 비슷한 모든 레시피를 판별하는 기능은 아니다.
추천 요청 시에는 별도의 `dish_family`로 동일 음식을 한 번만 표시한다. 공백/문장부호,
계란/달걀·쇠고기/소고기·무우국/뭇국 등의 표기 차이와 일반적인 수식어를 정리한다.
음식 이름 전체를 알려진 재료명과 조리명으로 해석할 수 있는 경우에만 재료명 순서도
통일한다(베이컨떡말이/떡베이컨말이, 참치김치볶음밥/김치참치볶음밥).
재료 조합이 달라도 같은 음식이면 선택 재료를 모두 포함한 후보 중 부족 재료가 가장 적은
변형 하나를 선택한다. 이 묶음 처리는 30개 제한 전에 수행하므로 같은 음식 30개를 가져온 뒤
줄여 버리는 문제가 없다. 원본의 변형 레시피와 의미 있는 음식명 수식(참치김치볶음밥 등)은 보존한다.

`source_total`은 보관한 자료 수, `catalogue_count`와 `sources`는 추천 대상 수다.
`quality_excluded`에는 제외 이유별 건수를 기록한다. 재검토가 필요하면 Git 밖의
`RECIPE_DATA_DIR/quality_overrides.json`에 `{"10000recipe:123": "include"}` 또는
`"exclude"`를 설정하고 전체 통합 명령을 다시 실행한다. include는 해당 자료를 별도
추천 대상으로 복원한다. 원본 CSV와 정상 동작 중인 색인은 수집 실패 시 유지한다.

자료 재수집 없이 전체 재검사:
`python -m scripts.review_recipes`는 현재 색인을 복사해 미리 검사하며,
`python -m scripts.review_recipes --apply`는 성공한 결과만 원자적으로 적용한다.
각 실행은 Git 밖의 `RECIPE_DATA_DIR/quality-review-v4.csv`에 전체 레코드의 ID·추천 여부·
제외 이유·제목·요리명·출처·원문을 기록한다. 서비스 중인 자료와 원본은 검사 실패 시 유지한다.

## 데이터 출처와 현재 규모

- 식품의약품안전처 **조리식품의 레시피 DB(COOKRCP01)**
- 공식 안내/인증키 신청: https://www.foodsafetykorea.go.kr/api/openApiInfo.do?svc_no=COOKRCP01
- 공공데이터포털: https://www.data.go.kr/data/15060073/openapi.do
- 2026-10-28 공식 sample 응답의 전체 건수: **1,156건**. 건수는 수집 때 다시 확인한다.
- 인증키 없이 허용된 공식 샘플은 **5건**이다. 앱에서 샘플임을 표시한다. 전체 자료가 이미 들어 있는 것처럼 표시하지 않는다.
- 레시피 원문 재료/조리 순서와 출처를 상세에 표시한다. 이미지 파일은 복제하지 않는다.
- 다른 대규모 사이트의 공개 페이지가 곧 재배포 허가를 의미하지는 않는다. 만개의레시피 등 별도 출처를 추가할 때는 조리 순서 제공 여부와 해당 상품의 이용/재배포 조건을 먼저 확인해야 한다. 공식 출처의 현행 이용조건을 배포 시 재확인한다.

## 가져오기

식품안전나라 로그인 → 인증키 신청 → COOKRCP01 이용 신청. 발급받은 키를 서버 `.env`에 넣는다. 공공데이터포털의 일반 서비스키와 혼동하지 않는다.

```dotenv
FOODSAFETY_API_KEY=발급받은_키
```

```sh
python3 -m scripts.prepare_recipes
docker compose up --build -d
docker compose run --rm --no-deps api python -m scripts.import_recipes
```

`run`은 최신 `.env`를 읽는다. 이미 떠 있는 컨테이너에서 `exec`만 하면 변경 전 환경 변수를 사용할 수 있다.
키가 없을 때 기능 확인용:

```sh
docker compose run --rm --no-deps api python -m scripts.import_recipes --sample
```

1회 최대 1,000건씩 전체 페이지를 수집한다. 전체 건수/중복/빠진 페이지를 검사한 다음 원본 SHA256과 수집 시각을 기록하고 색인 파일을 원자적으로 교체한다. 실패하면 기존 자료를 유지한다. 샘플로 전체 자료를 덮어쓰지 않는다. 런타임은 파일 변경 시 다시 읽으므로 앱/서버 재빌드 없이 추천을 새로 불러오면 적용된다. 원본 보관 파일은 수집 버전별로 쌓이므로 보관 정책에 맞춰 오래된 백업을 정리한다.

## GitHub와 배포

Git에 포함: 가져오기 코드, 정규화/매칭 규칙, 테스트, 이 안내 문서.
Git과 기본 Docker 빌드 컨텍스트에서 제외: `.env`, `recipe_data/`, 원본 JSON, 생성된 색인, 사용자 DB, 업로드 사진.
개발 빌드는 별도 컨텍스트인 `recipe_data/image-seed/`에서 검증된 레시피 DB와 manifest만 가져온다.

로컬 Compose의 `recipe_data` named volume(`/app/recipe_data`)에 저장한다. 서버 컨테이너 교체로 자료가 사라지지 않는다. `docker compose down -v`는 사용자 DB와 레시피 볼륨까지 삭제하므로 사용하지 않는다.

운영에서는 전용 데이터 갱신 작업이 수집 후 `catalogue.json`과 SHA256 manifest를 S3/GCS 같은 비공개 객체 저장소에 버전별로 올리고, 검증된 파일을 각 서버의 읽기 전용 마운트/캐시에 배포한다. 지금 구현은 로컬 파일을 읽으며 **S3/GCS 자동 업로드는 구현하지 않았다**. Cloud Run의 일시적인 로컬 디스크에는 유일한 사본을 두지 않는다. `RECIPE_DATA_DIR`를 마운트 위치로 설정한다. 인증키는 서버 secret manager에만 저장하며 `EXPO_PUBLIC_` 변수로 노출하지 않는다.

## 추천 계약

- `POST /fridges/{id}/recipes/recommendations`에 `{ "item_ids": [1, 2] }`.
- 냉장고 멤버만 접근 가능. 다른 냉장고/이미 소진된 식품 ID는 409. 빈 선택은 빈 추천.
- 냉장·냉동·실온 구분 없이 선택한 활성 식품을 사용. 소비기한이 지난 식품은 제외하고 응답에 명시.
- 계란/달걀 등 명칭 정규화. 삼겹살 → 돼지고기는 허용하지만 역방향 대체는 하지 않는다. 연두부/두부, 저염간장/간장은 구분한다.
- 선택한 재료가 모두 한 레시피에 들어가고 주재료가 하나 이상 맞는 레시피만 최대 30개. 재료별 개별 레시피로 대체하지 않으며, 전체 조합이 없으면 빈 목록을 반환한다. 부족 재료 0개, 1개, 2개 순으로 추천하며 같은 부족 개수 안에서는 요청마다 무작위로 섞는다. 30개 제한 전에 섞어 동순위 후보도 매번 달라질 수 있다. 모든 양념도 보유 여부를 비교한다.
- 중량/개수 단위 변환은 하지 않으므로 '조리 가능'을 확정하지 않는다. 부족 재료와 원문 분량을 보여준다. 원문 자유 서술형 재료 자동 분석에는 한계가 있다.
- `GET /fridges/{id}/recipes/{recipe_id}`에서 원문 재료, 비어 있지 않은 조리 단계, 팁, 출처 제공.

## 검증

```sh
docker compose run --rm --no-deps api pytest -q tests/test_recipes.py
```

실제 계정의 식재료/예시 데이터를 만드는 코드나 seed는 포함하지 않는다. 테스트는 독립 SQLite DB를 사용한다.

## 개발용 데이터 준비와 Docker 실행

데이터 준비와 Docker 빌드·실행은 별도 단계다. 서버 저장소 루트에서 최초 한 번 실행한다.

```sh
gh auth login
python3 -m scripts.prepare_recipes
docker compose up --build -d
```

`prepare_recipes`는 데이터를 준비하고 종료한다. Docker를 호출하거나 서버를 시작하지 않는다.
비공개 데이터 저장소에 접근할 수 있는 GitHub 계정으로 gh에 로그인해야 한다.
호스트 Python 3.11+가 필요하며, Docker 빌드에는 Compose 2.17+가 필요하다.
이미 받은 ZIP은 다음과 같이 사용한다. 이 경우 준비 과정에 gh가 필요 없다.

```sh
python3 -m scripts.prepare_recipes --package /absolute/path/to/package.zip
docker compose up --build -d
```

다운로드할 저장소·릴리스·파일명·데이터 버전·DB 체크섬·품질 버전은 저장소 루트의
[`recipe-package.json`](../recipe-package.json)에서 관리한다.
설정 필드는 `repository`, `release`, `asset`, `package_version`, `sha256`, `quality_version`이다.
다운로드한 DB는 설정과 manifest를 대조하고, SHA-256·SQLite 무결성·테이블·스키마·건수·
추천 대상의 최소 재료 수 검사를 통과한 뒤 `recipe_data/image-seed/`에 보관한다.
이 경로는 Git에서 제외되며 버전이 바뀌어도 경로명은 바꾸지 않는다.
동일한 데이터가 이미 준비되어 있으면 검증 후 재사용한다. 이전 방식의
`recipe_data/image-seeds/*`에 맞는 자료가 있으면 검증해 새 경로로 옮겨 사용할 수 있다.
다운로드 ZIP과 검증용 임시 파일은 정리하고, 다음 빌드에 필요한 DB와 manifest는 유지한다.
다운로드·검증 실패 시 기존에 준비된 데이터는 보존한다.

평소 코드 변경은 다음 명령만 실행한다.

```sh
docker compose up --build -d
```

Compose는 로컬의 준비된 DB를 이미지의 `/opt/recipe-seed/`에 포함한다.
빌드 중 데이터 다운로드나 GitHub 인증은 수행하지 않으며, 설정 파일과 준비된 DB가
일치하는지 오프라인으로 검사한다. 최초 준비를 하지 않았거나 설정과 DB가 다르면
빌드가 실패하므로 `python3 -m scripts.prepare_recipes`로 준비한 뒤 다시 빌드한다.
이미지에는 압축을 푼 약 870MB DB가 추가된다. GitHub 인증정보는 이미지나 컨테이너에 넣지 않는다.

데이터 버전을 갱신할 때는 `recipe-package.json`만 변경한 뒤 다음 두 단계를 실행한다.

```sh
python3 -m scripts.prepare_recipes
docker compose up --build -d
```

서버 시작 시 `/opt/recipe-seed/`와 실제 `recipe_data` 볼륨의 DB를 비교한다.
없거나 체크섬이 다르면 새 자료를 검증한 뒤 기존 레시피 DB를 백업하고 원자적으로 교체한다.
같은 자료면 백업·교체 없이 시작한다. 검증 실패나 SQLite sidecar가 있으면 서버 시작을
중단하고 기존 파일을 유지한다. 수집·재검사 등 다른 작성 작업과 동시에 실행하지 않는다.
백업 파일은 `recipe_data` 볼륨에 남으며 자동 삭제하지 않는다. 사용자 DB·업로드·`.env`는
레시피 준비와 설치 과정에서 수정하지 않는다.

이 자동 초기화는 개발용 `development` 타깃과 `docker-compose.yml`에 적용한다.
운영·Cloud Run 타깃에는 적용하지 않는다. 운영은 영속 마운트와 권한을 별도로 구성해야 한다.
Cloud Run 이미지는 자동 초기화 없이, 같은 `recipe_data/image-seed/`의 검증된 DB를 빌드 때 읽기 전용으로 넣는다 ([deploy/CLOUD_RUN.md](../deploy/CLOUD_RUN.md)의 "레시피 데이터 준비").
이미지를 공유할 때도 데이터 출처의 이용 조건에 따라 비공개로 보관한다.
고정 버전과 다른 자료가 볼륨에 있어도 이미지 자료로 백업 후 교체하므로,
로컬에서 재수집한 DB를 유지하려면 해당 DB를 고정 배포 데이터로 갱신하거나 별도 실행 환경을 사용한다.

기존 `python3 -m scripts.start_with_recipes` 명령은 호환용 별칭이다.
이제 데이터 준비만 수행하고 Compose 실행 명령을 안내하며, 자동으로 빌드하거나 서버를 실행하지 않는다.

## 로컬 서버용 수동 설치

Docker 자동 설치 대신 실제 `RECIPE_DATA_DIR`에 직접 설치할 때 사용하는 하위 도구다.
서버·앱의 호환 코드를 준비한 뒤, 받은 ZIP 경로와 실제 서버 데이터 경로를 지정한다.
`.env`를 자동으로 읽지는 않는다.

```sh
python3 -m scripts.install_recipe_package /absolute/path/to/package.zip --data-dir /absolute/server/recipe_data
# 검증 성공 후 같은 명령에 --apply를 붙여 설치
```

기본 실행은 검증만 수행한다. 대상 폴더에 임시 파일과 설치 잠금 파일을 만들지만
기존 DB는 바꾸지 않는다. `--apply`는 검증한 파일을 같은 파일시스템에서 원자적으로 교체하고,
기존 DB를 `recipes.sqlite3.backup-<UTC 시각>`으로 보존한다.
압축 해제용 약 870MB와 기존 DB 백업을 포함한 여유 공간이 필요하다.
실패하면 기존 DB를 유지하며, 수집·재검사 등 다른 DB 작성 작업과 동시에 실행하지 않는다.
설치 후 앱에서 추천을 새로 요청해 실제 결과를 확인한다.
